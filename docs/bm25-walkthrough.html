01

The shape of the thing

Bm25Index is a one-class wrapper around a JSON file (the sidecar) that Bm25IndexWriter dropped on disk during ingestion. The constructor loads the file once, walks every entry, and builds an in-memory inverted index. After that, the three tool functions returned by tools() just consult the in-memory tables — no further disk reads.

Solid = called once during __init__. Dashed = called per query. Terracotta border = the public surface (everything else is private).

03

Tokenization — the foundation

Every other step is downstream of _tokenize. It's deliberately boring: lowercase, then \w+ Unicode word runs. No stemming, no stopwords, no synonyms. The reason is fidelity — tokens correspond to exact substrings, so snippets and citations always quote the source verbatim.

# reigner/tools/search/bm25.py:34, 38
_TOKEN_RE = re.compile(r"\w+", re.UNICODE)

def _tokenize(text: str) -> list[str]:
    return [m.group(0).lower() for m in _TOKEN_RE.finditer(text)]
Punctuation and whitespace become separators for free. "R&D — $30B" → ["r", "d", "30b"]. That's a known limitation — see Future scope.
04

_build — assembling the inverted index

One pass over every entry. For each one, count token frequencies (tf), bump the document frequency (df) for every distinct token seen, record the document length (dl), and sum lengths to compute avgdl.

# reigner/tools/search/bm25.py:123
def _build(self) -> None:
    total_len = 0
    for entry in self._entries:
        tokens = _tokenize(entry.get("text", "") or "")
        self._doc_tokens.append(tokens)
        tf: dict[str, int] = {}
        for tok in tokens:
            tf[tok] = tf.get(tok, 0) + 1
        self._tf.append(tf)
        self._doc_len.append(len(tokens))
        total_len += len(tokens)
        for tok in tf:           # df = doc-level, not token-level
            self._df[tok] = self._df.get(tok, 0) + 1
    self._avgdl = (total_len / self._N) if self._N else 0.0

Why df is per-document, not per-token. The inner loop iterates for tok in tf — the unique tokens — not over the flat token list. Repeated occurrences in one doc count once towards df. That's the standard BM25 definition; idf measures rarity across documents, not within them.
05

_score_doc — the actual BM25 formula

BM25 — Robertson/Sparck-Jones with Lucene's idf smoothing
score(q, d) = Σt∈q   idf(t) · ( tf(t,d) · (k1+1) ) / ( tf(t,d) + k1 · (1 − b + b · dl / avgdl) )

idf(t) = ln( 1 + (N − df(t) + 0.5) / (df(t) + 0.5) )

Each term contributes only if it appears in the doc (term_freq == 0 short-circuits). The denominator's length normalization shrinks the contribution when dl > avgdl — i.e. long docs don't win by being long.

# reigner/tools/search/bm25.py:138
def _score_doc(self, query_tokens: list[str], doc_idx: int) -> float:
    if self._avgdl == 0.0:
        return 0.0
    dl = self._doc_len[doc_idx]
    tf = self._tf[doc_idx]
    score = 0.0
    for term in query_tokens:
        df = self._df.get(term, 0)
        if df == 0: continue            # term not in corpus
        term_freq = tf.get(term, 0)
        if term_freq == 0: continue     # term not in this doc
        idf  = math.log(1 + (self._N - df + 0.5) / (df + 0.5))
        norm = term_freq * (_K1 + 1) / (term_freq + _K1 * (1 - _B + _B * dl / self._avgdl))
        score += idf * norm
    return score

A real query, scored by hand

Query: "apple cherry" → tokens [apple, cherry]. We score each doc. Because both query terms have df = 2 and N = 3, the idf is the same for both:

idf(apple) = idf(cherry) = ln( 1 + (3 − 2 + 0.5) / (2 + 0.5) ) = ln(1.6) ≈ 0.4700

doc-a (dl=3, tf[apple]=2, tf[cherry]=0)

norm(apple) = 2·2.5 / (2 + 1.5·(0.25 + 0.75·3/3.333))
     = 5 / (2 + 1.5·0.925) = 5 / 3.3875 ≈ 1.4760
apple → 0.4700 · 1.4760 ≈ 0.6937
cherry → tf=0, skipped
score(doc-a) ≈ 0.6937

doc-b (dl=4, tf[apple]=0, tf[cherry]=1)

norm(cherry) = 1·2.5 / (1 + 1.5·(0.25 + 0.75·4/3.333))
     = 2.5 / (1 + 1.5·1.15) = 2.5 / 2.725 ≈ 0.9174
cherry → 0.4700 · 0.9174 ≈ 0.4312
score(doc-b) ≈ 0.4312

doc-c (dl=3, tf[apple]=1, tf[cherry]=1)

norm(apple) = norm(cherry) = 1·2.5 / (1 + 1.5·0.925) = 2.5 / 2.3875 ≈ 1.0471
apple → 0.4700 · 1.0471 ≈ 0.4921
cherry → 0.4700 · 1.0471 ≈ 0.4921
score(doc-c) ≈ 0.9842   winner
The intuition. doc-c wins because it covers both query terms even though each appears only once. doc-a has high tf for "apple" but contributes nothing for "cherry". doc-b matches only "cherry" and gets length-penalized (dl > avgdl). BM25's saturating tf curve — that's the tf·(k1+1)/(tf+...) shape — is what keeps doc-a from running away on raw repetition.

07

_search_text — the orchestrator

This is what bm25_search actually calls. It glues the pieces together: validate filters, tokenize, score every (filtered) doc, sort, truncate, format.

# reigner/tools/search/bm25.py:167 — abridged
def _search_text(self, query, raw_filters, top_k):
    if not self._entries:
        return _empty_result(note=_MISSING_INDEX_NOTE)   # 1
    filter_ = parse_filters(raw_filters)                  # 2
    tokens  = _tokenize(query)
    if not tokens:
        return _empty_result()                          # 3
    scored = []
    for idx, entry in enumerate(self._entries):
        if filter_ and not matches(entry["identifiers"], filter_):
            continue                                       # 4
        score = self._score_doc(tokens, idx)
        if score > 0.0: scored.append((score, idx))     # 5
    scored.sort(key=lambda p: (-p[0], self._entries[p[1]]["id"]))  # 6
    hits = [self._format_hit(...) for score, idx in scored[:top_k]]
    return {"hits": hits,
            "total_matches": len(scored),
            "has_more": len(scored) > top_k,           # 7
            "truncated": False}
  1. Missing index guard. Empty entry list → return an empty result plus a note. The model sees "index not built; run reigner ingest" and can react.
  2. Filter parsing. Coerces & validates the filter dict (see filters.py). Throws on malformed input.
  3. Empty query. Whitespace-only or tokenizes to nothing → empty result, no note. The public tool function rejects whitespace queries earlier with ValueError.
  4. Filter short-circuits scoring. Non-matching docs never hit _score_doc, which matters at scale.
  5. Score > 0 keeps a doc. Zero-score docs are dropped: no query term matched.
  6. Stable sort. Primary: score descending. Tiebreaker: id ascending — deterministic ordering even when BM25 ties.
  7. has_more / total_matches. The self-describing fields that let an agent know there's more to fetch (PRINCIPLES.md §2).
08

The other two tools

_search_filtered — no scoring, just enumeration

When the agent already knows what it's looking for (e.g. "give me every AAPL 10-K from 2022–2024"), scoring is wasted work. filtered_search returns matching entries sorted by id ascending, with a snippet but a score: 0.0.

_search_section — per-call mini-index over one section

The sidecar stores each entry's sections dict ({"document_summary": "...", "risk_factors": "..."}). When the agent calls section_search(query, section_name), the method builds a fresh inverted index just for that section across all docs, then scores against it. N, avgdl, df — all recomputed from the section corpus, not the whole-doc corpus. That's why a frequent term inside risk_factors still has meaningful idf if it's rare across other docs' risk_factors sections.

Legacy fallback. Old sidecars (written before sections were stored) don't have a sections key. section_search notices, returns no hits, and includes a note telling the user to re-run reigner ingest — never raises.
09

_snippet — quoting the source faithfully

For every hit, _snippet finds the earliest matched query token in the text, then expands ±120 characters around it, snapping out to the nearest non-alphanumeric boundary so we don't slice a word in half. Ellipses (…) mark truncation on either side.

Example. Text: "Risk factors for the fiscal year: ongoing litigation in the EU materially affects forward guidance. See note 14."
Query tokens: [litigation]

earliest match → "litigation" at index 39
window → [max(0, 39-120) … min(len, 39+120)] = [0, 159] → whole string fits
result → "Risk factors for the fiscal year: ongoing litigation in the EU materially affects forward guidance. See note 14."

Degenerate inputs, by design

Every "thing that could go wrong with the sidecar" resolves to empty result + note, never an exception. The model treats the note as a signal to call a different tool or ask the user.

What the agent actually sees

The @tool(readonly=True, cache=True) decorator wraps each closure. readonly means the harness can call it speculatively without confirmation; cache means identical (query, filters, top_k) tuples are deduped under G9 — handy when an agent re-issues the same search across reasoning steps.

12

Things worth knowing for later

The whole index is in memory

One process load. For tens of thousands of compiled docs this is fine; for millions, the in-memory dict-of-dicts becomes the bottleneck before BM25 math does. The SearchIndex Protocol is the escape hatch — swap in a SQLite-FTS or vector backend without touching the harness.

Section search rebuilds its index on every call

Deliberate. section_search is the rarer of the three tools, and per-section corpora are small. The alternative — pre-building a per-section inverted index for every section name at startup — wastes memory when most queries don't use it. If profiling shows section_search dominating, cache per-section indexes lazily.

Tokenizer fidelity vs. recall

Strict \w+ lowercase keeps snippets honest but loses on "R&D" → ["r", "d"] and Unicode-normalization edge cases. Adding stemming or stopwords would help recall but break the substring-fidelity guarantee that snippets and citations depend on. Any change here is a Principle-level decision, not a tuning knob.
