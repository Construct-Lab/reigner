Milestones

Four slices. README first (self-contained, high visibility), then the site it links to (built and reviewed locally), then retiring/scrubbing the planning docs. Deploy is deliberately last and gated: the site only goes public after you've read the full rendered docs and issue #126 (FastAPI + observability testing) is done. The Observability walkthrough moves out to a docs page (a one-line pointer stays). Nothing depends on the site existing yet — the docs link is a known URL.

05

Key code

The two configs easiest to get wrong: the mkdocs.yml that must render root docs and exclude generated HTML, and the mike deploy job's permissions.

mkdocs.yml — nav, exclude generated HTML, render root docs
site_name: Reigner
site_url: https://construct-lab.github.io/reigner/
repo_url: https://github.com/Construct-Lab/reigner
theme:
  name: material
  features: [navigation.sections, search.suggest, content.code.copy]

plugins:
  - search
  - include-markdown           # pulls root SPEC.md / PRINCIPLES.md in
  - mkdocstrings: { handlers: { python: { paths: [.] } } }

# docs_dir stays ./docs — drop the committed HTML plans/reviews from the build
exclude_docs: |
  *.html
  plan/
  review/

nav:
  - Overview: index.md
  - Guide:
    - Usage: guide/usage.md
    - Observability: guide/observability.md
  - Design:
    - Spec: design/spec.md
    - Principles: design/principles.md
  - API reference: reference.md
.github/workflows/docs.yml — unversioned deploy (mike deferred)
on:
  push: { branches: [main] }

permissions:
  contents: write              # push the built site to gh-pages

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
      - run: uv sync --group docs
      - run: uv run mkdocs gh-deploy --force   # build + push to gh-pages

Future scope & assumptions

Deliberately out of this plan, plus assumptions I made that are worth a look during review.

Terminal demo GIF in the README?

You deferred it earlier. A short asciinema/GIF of reigner chat producing a cited answer is the single highest-impact way to make "citation-faithful" tangible — the way FastAPI's Swagger screenshot sells auto-docs. Not in these slices; easy to slot into the README quickstart later.

Decide with · you · after the site is live

Positioning: one core, three surfaces

Docs lead with Reigner as a toolkit for building citation-faithful QA agents over a knowledge corpus, met at three points on one core: build (the library — schema, @tools, extractor, recipe, plugins), test (the CLI — ingest, chat, fork/replay/diff, eval), ship (the server — serve --http, FastAPI/SSE). The library is the hero, not the CLI — so the Overview must not read as "a chat CLI." Caveat baked in: serve --mcp is stubbed, so the ship surface is "FastAPI/SSE today, MCP planned" — never implied as working.

Decide with · you · Slices 1 & 2 (README + index.md)

Scrub "ApolloScope" before SPEC/PRINCIPLES go public

Both files name an internal predecessor system ("ApolloScope") — 3 mentions in PRINCIPLES, ~11 in SPEC including a whole Appendix B mapping table. That's meaningless and inappropriate in public OSS docs. Plan: keep principle §2 but reframe it generically (the "build fresh, don't port" idea is valuable; the internal name is not), genericize SPEC's inline mentions to "a production document-QA system" / "the reference layout", and delete Appendix B outright. Open call: reframe vs. remove principle §2 — I recommend reframe.

Decide with · you · Slice 4 (before first publish)

Assumption: root SPEC/PRINCIPLES stay put, rendered via include-markdown

I'm keeping SPEC.md and PRINCIPLES.md at repo root (where contributors expect them) and rendering them into the site through thin stub pages, rather than moving them under docs/. The alternative — symlinks into docs/ — is simpler but flakier across checkouts. If you'd rather move them outright, that changes the stub files. Also: SPEC has aspirational sections; it needs a short "status" note up top so the site doesn't read unbuilt features as shipped.

Decide with · you · Slice 2

Assumption: resolve the docs/ gotcha via exclude_docs, not a move

Issue #76 offered two options. I picked keeping docs_dir = ./docs and excluding the generated HTML, and moving only prose under docs/guide/. This keeps the visualise-plan / review-board HTML output landing where it already does (and staying uncommitted per convention) without fighting the build.

Decide with · you · Slice 2

Custom domain (reigner.dev)?

Launch on the default construct-lab.github.io/reigner URL. A custom domain is a later CNAME file + DNS change; no code impact and no reason to block release on it.

Decide with · you · post-launch

ROADMAP.md to replace TASKS.md?

Leaning no — GitHub Projects is enough public forward-view for now. A user-facing ROADMAP only earns its place once there's a real "what's coming" story to tell.

Decide with · you · when the story exists

Manual step outside the diff

The first deploy needs Settings → Pages → source = "GitHub Actions" flipped once by an org owner. The Action can't do this itself; it's a one-time click, called out so it doesn't silently block the first publish.
