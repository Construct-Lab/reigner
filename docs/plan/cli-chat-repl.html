Key code

The four bits most likely to be done wrong: steer unstub, key bindings, the run-task cancellation dance, and the test-only adapter.

reigner/harness/agent.py — Session.steer
async def steer(self, message: str, mode: SteeringMode = "interrupt") -> None:
    """Enqueue a steering message. Consumed at the next loop boundary."""
    self._state.add_steering(message, mode)
reigner/cli/chat.py — prompt_toolkit key bindings
kb = KeyBindings()

@kb.add("enter")
def _enter(event):
    text = event.app.current_buffer.text.strip()
    if not text:
        return
    if running.is_set():
        # mid-run: steer interrupt
        asyncio.create_task(session.steer(text, "interrupt"))
        event.app.current_buffer.reset()
    else:
        # idle: submit as new query
        event.app.exit(result=text)

@kb.add("escape", "enter")  # Alt+Enter
def _alt_enter(event):
    text = event.app.current_buffer.text.strip()
    if text and running.is_set():
        asyncio.create_task(session.steer(text, "queue"))
        event.app.current_buffer.reset()
reigner/cli/chat.py — run-task with Ctrl+C cancel
async def _drive(session, query, render):
    running.set()
    try:
        async for ev in session.run_stream(query):
            render(ev)
    except asyncio.CancelledError:
        render_cancelled()
    finally:
        running.clear()

# bound to Ctrl+C in the prompt session
@kb.add("c-c")
def _ctrl_c(event):
    if running.is_set() and current_task is not None:
        current_task.cancel()
    else:
        event.app.exit(exception=KeyboardInterrupt)
tests/cli/conftest.py — FakeAdapter
class FakeAdapter:
    """Yields a scripted sequence of Actions ending in is_final_answer."""
    def __init__(self, script: list[Action]):
        self._script = list(script)

    async def call(self, prompt, tools) -> Action:
        return self._script.pop(0)

def make_harness(script, tools=None) -> Harness:
    return Harness(adapter=FakeAdapter(script), tools=tools or [], role="test")
06

Future scope

What T-19 deliberately does not solve, plus the assumptions baked in.

Should chat support --resume <session_id>?

Out of scope: Session.load / .save are stubbed pending T-23. Adding it here would mean pulling forward a second deferred subsystem on top of the steer unstub, which is the kind of scope creep this task is supposed to avoid. Revisit when T-23 lands.

Decide with · session-persistence work (T-23)

Live-updating widgets vs scroll-back log

Assumption: compact status lines + a final-answer Panel beat a live spinner / collapsible tree. Easier to copy-paste from the terminal, plays nicely with patch_stdout, and avoids redraw flicker over SSH. If feedback during M2 says it feels too noisy, we add a --quiet flag rather than rebuilding the renderer.

Decide with · M2 dogfooding

Pulling Session.steer forward from T-06

The wiring is genuinely tiny — one delegation to state.add_steering — and the REPL is unusable without it. T-06's broader scope (cancellation semantics for in-flight tool calls, dropping queued parallel calls on interrupt) still lives in T-06; we are only exposing the existing state surface through the Session wrapper.

Decide with · T-06 owner before merge

Windows / non-TTY behaviour

Assumption: interactive REPL targets a real TTY on macOS/Linux. If stdin is not a TTY (CI, piped input) and --print is not passed, we error out with a clear message rather than trying to read line-buffered input. --print remains the canonical headless entry point.

Decide with · first Windows user report

Clarification events in the REPL

Assumption: when the loop emits a ClarificationEvent, the REPL renders the question and candidates, then waits at the prompt for the user to type their answer — which gets sent as the next query. No special UI affordance (yet). --print mode exits non-zero on clarification because there's no human to answer.

Decide with · first real eval recipe (T-32)
