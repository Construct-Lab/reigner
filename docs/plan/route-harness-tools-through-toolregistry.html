Data flow

Two diagrams. The first shows how a registry is born inside Harness.from_config (config-time wiring). The second shows what the loop sees at runtime when a Session with a non-full profile drives a turn.

Build-time: one ToolRegistry per Harness, populated from four sources in a fixed order. Solid = call. Dashed = exception path. Terracotta = new or refactored module.
Runtime: the loop never sees the unfiltered surface — every turn it asks for_profile(state.profile) and rebuilds tools_by_name. Pseudo-tools are dispatched inline; real calls go through execute_batch which calls adapter.run(args). Solid = sync. Dashed = async event yield. Terracotta = changed module.

Key code

The two snippets that govern correctness: the registry's accept-and-wrap behaviour, and the loop's per-turn filtered view.

reigner/tools/registry.py
def register(self, x: Callable[..., Any] | ToolSpec | RunnableToolAdapter) -> ToolSpec:
    if isinstance(x, ToolSpec):
        spec = x
    elif isinstance(x, RunnableToolAdapter):
        spec = x.spec
    else:
        spec = _spec_of(x)          # reads __reigner_spec__ off @tool callable
    if spec.name in self._specs:
        raise ToolRegistrationError(f"tool {spec.name!r} is already registered")
    self._specs[spec.name] = spec
    return spec

def for_profile(self, profile: Profile) -> list[RunnableToolAdapter]:
    if profile == "full":
        specs = list(self._specs.values())
    elif profile == "read_only":
        specs = [s for s in self._specs.values() if s.readonly or s.pseudo]
    elif profile == "eval":
        specs = [s for s in self._specs.values()
                 if (s.readonly or s.pseudo) and s.name not in _EVAL_EXCLUDED]
    else:
        raise ValueError(f"unknown profile: {profile!r}")
    return [RunnableToolAdapter(spec=s) for s in specs]
reigner/harness/loop.py — top of run_loop
# Per-turn filtered surface. Profile is fixed for the session's lifetime,
# so this re-filter is cheap and the result is stable across iterations.
runnables = state.registry.for_profile(state.profile)
tools_by_name: dict[str, RunnableTool] = {a.name: a for a in runnables}

# …later, when calling the model adapter:
action = await adapter.call(prompt, runnables)
# execute_batch indexes by name; pseudo-tools never enter tools_by_name
# because PSEUDO_TOOL_NAMES is filtered out before _run_real_calls.

Custom-profile registration

Today profiles are a fixed Literal["full","read_only","eval"]. A library user can't yet say "give me a profile that's read_only minus bm25_search". Defer until a real need surfaces — the registry is the right home for it later.

Decide with · whoever hits the need first

Assumption · registry + profile both live on AgentState

The issue's wording mixed state.registry with session.profile. I'm putting both on AgentState so run_loop needs no signature change — every loop input continues to come off state. Session still owns the public profile (it's read at construction and passed through); the duplication is one assignment, not a sync problem.

Decide with · reviewer · during PR

Assumption · Harness drops the tools= field entirely

Direct construction becomes Harness(adapter=..., registry=ToolRegistry()). Any test that built a Harness with a bare tool list will be updated to build a registry. We considered keeping tools= as a convenience but it muddies the acceptance criterion (list(h.registry)) and gives two ways to do the same thing.

Decide with · reviewer · during PR

Assumption · for_profile() wraps on every call

Each call constructs fresh RunnableToolAdapter instances. With ~10 tools per harness and one filter per turn, the allocation cost is negligible. If profiling later flags it, memoise per-profile inside the registry.
