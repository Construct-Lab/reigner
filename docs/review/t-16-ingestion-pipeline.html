Where we were

The starting point

SPEC §8 splits ingestion into three layers: A (ArtifactSchema, the declared shape), B (LLMExtractor, the user's prompt + parse), and C (the runner that walks a directory and turns the first two into compiled artifacts on disk).

Layers A and B were already in place. ArtifactWriter (T-13) knew how to atomically lay down one entity's files; LLMExtractor (T-14) knew how to call a model and validate the result; the four loaders (T-15 — PdfLoader, MdLoader, JsonLoader, UrlLoader) knew how to read one source into (bytes, meta). What was missing was the wiring: no caller could yet say "compile this folder of raw PDFs into the artifact tree."

Why this is the integration moment: downstream tasks all assume a working pipeline. The CLI's reigner ingest (T-20), the document_qa recipe (T-32), and the SEC 10-K example (T-34) are all thin consumers of pipeline.run(source). Until Layer C exists, the three artifact layers are functional in isolation but produce nothing end-to-end.

Architecture

The shape of one run

pipeline.run(source) is the user-facing one-liner. pipeline.run_stream(source) is the streaming variant — same machinery, yields StatusEvent / ErrorEvent instances as workers complete. The final report is available on pipeline.last_report after the stream drains.

pipeline.run(source: path-or-file) │ ▼ _discover(source) sorted file list, filtered by │ ext-to-loader map built at __init__ ▼ yield StatusEvent("discovered N sources") │ ▼ asyncio.Semaphore(concurrency) │ ▼ for each src (parallel up to concurrency): ┌──────────────────────────────────────────────────────────┐ │ worker(src) -> list[Event] │ │ loader.load(src) -> LoadedDocument │ │ identifiers_fn(loaded) -> {key: str, ...} │ │ ┌─ _is_already_extracted? -> report.skipped++ done │ │ └─ no │ │ transform.run(raw, meta) -> ExtractionResult │ │ for writer in writers: │ │ ArtifactWriter -> write_entity(**ids, ...) │ │ PipelineWriter -> .write(loaded, result, ids) │ │ report.succeeded++ │ │ events.append(StatusEvent("completed ...")) │ │ │ │ on Exception (anywhere above): │ │ on_error="raise" -> re-raise (cancels rest) │ │ on_error="skip" -> ErrorEvent + log failure │ │ on_error="dead_letter" -> + write raw + error.json │ └──────────────────────────────────────────────────────────┘ │ ▼ asyncio.as_completed(tasks) yield each worker's events in completion order │ ▼ yield StatusEvent("ingestion complete: N ok, M failed, K skipped") │ ▼ pipeline.last_report = IngestionReport(...)
Why all five guarantees live in one class: the SPEC §8.3 promises — concurrency, progress, idempotency, error policy, final report — are tightly coupled. The cache key, the failure routing, and the report counters all want to see the same per-source context. Splitting them into separate orchestrators would require passing that context around through a second layer of state.
Design call

Identifiers — the pre-extraction seam

ArtifactWriter.write_entity takes **identifiers — the dict that fills the schema's entity_path template (e.g. {"ticker": "AAPL", "fiscal_year": "2024"}). The pipeline has to produce that dict from somewhere. There were two honest answers:

  • (A) Pull identifiers from result.meta["identifiers"] after extraction. Closest to the existing LLMExtractor code path, but means idempotency can't be decided until after the expensive model call.
  • (B) A pre-extraction identifiers_fn(loaded) -> dict hook operating on LoadedDocument.meta alone (which the loader's own meta_extractor populated from the filename).

This PR ships (B):

def _default_identifiers_fn(loaded: LoadedDocument) -> dict[str, Any]:
    ids = loaded.meta.get("identifiers")
    if isinstance(ids, dict):
        return dict(ids)
    return {}

Convention: a loader's meta_extractor writes a flat {"identifiers": {...}} dict into LoadedDocument.meta. Custom needs override via the constructor's identifiers_fn= argument.

Why pre-extraction wins: a 200-page 10-K costs cents and minutes per extraction. If identifiers came from the ExtractionResult, idempotency would only catch the already-written case after paying that cost. With the pre-extraction seam, the cache key is computable from cheap loader-derived metadata, and the model call is skipped entirely when the source has already been ingested under the same prompt + schema.
Tradeoff accepted: identifiers must be derivable from the source alone, not from extraction output. For most real corpora that's fine — the filename or URL is the natural primary key. The moment it isn't (e.g. the entity ID lives inside the PDF), the user has to either preprocess to surface that field or accept that every run hits the model. We didn't try to support both paths in v0.
Type dispatch

Writer dispatch — two shapes, one list

SPEC §8.3 shows the pipeline constructor taking a list mixing ArtifactWriter and Bm25IndexWriter: 

writers=[
    ArtifactWriter(root="library/artifacts", schema=schema),
    Bm25IndexWriter(path="search-index/documents.json"),
],

The two have genuinely different call signatures. ArtifactWriter.write_entity is synchronous, takes **identifiers as splat, and was built for T-13 without the pipeline in mind. The new writers want an async, uniform (loaded, result, identifiers) surface.

This PR adds a PipelineWriter protocol for the second shape:

@runtime_checkable
class PipelineWriter(Protocol):
    async def write(
        self,
        *,
        loaded: LoadedDocument,
        result: ExtractionResult,
        identifiers: dict[str, str],
    ) -> None: ...

…and dispatches inside the pipeline by isinstance: 

async def _invoke_writer(self, writer, loaded, result, identifiers):
    if isinstance(writer, ArtifactWriter):
        await asyncio.to_thread(
            _write_entity_blocking, writer, identifiers, result,
        )
    else:
        await writer.write(loaded=loaded, result=result, identifiers=identifiers)
Why isinstance and not a wrapper adapter: the alternative — wrapping ArtifactWriter in an ArtifactEntityWriter(PipelineWriter) adapter at insertion time — would force users to write a different import than the SPEC example shows. Two writer shapes is the actual complexity in the domain; hiding it behind a uniform adapter would obscure it. The dispatch is one branch in one method.
Why asyncio.to_thread for ArtifactWriter: the writer does synchronous file IO (staging dir + atomic rename). With concurrency=4 documents in flight, blocking the event loop on those writes would serialize the whole pipeline. The writer's own atomicity protocol uses per-call UUIDs in .staging/ so concurrent calls don't collide.
SPEC §8.3

Idempotency — what counts as "already ingested"

SPEC §8.3: "previously-ingested documents matching the current (source_hash, schema_version, prompt_hash) key are skipped." The transform protocol surfaces this tuple as a single opaque string: 

class Transform(Protocol):
    async def run(self, raw: bytes, meta: dict[str, Any]) -> ExtractionResult: ...
    def cache_key(self, raw: bytes) -> str: ...

LLMExtractor (T-14) already implemented cache_key() as "{source_hash}:{schema_version}:{prompt_hash}". The pipeline reconstructs the same string from the on-disk extraction_meta.json's extractor block and compares: 

def _is_already_extracted(self, loaded, identifiers):
    artifact_writers = [w for w in self._writers if isinstance(w, ArtifactWriter)]
    if not artifact_writers:
        return False                     # nothing canonical to anchor against
    if not identifiers:
        return False                     # can't resolve entity_dir without ids
    expected_key = self._transform.cache_key(loaded.raw)
    for writer in artifact_writers:
        entity_dir = writer.entity_dir(**identifiers)
        meta_path = entity_dir / writer.schema.extraction_meta
        if not meta_path.exists():
            return False
        manifest = ExtractionMeta.from_json(meta_path.read_text())
        existing_key = _manifest_cache_key(manifest)
        if existing_key != expected_key:
            return False
    return True
Why all three of those early-returns matter: idempotency must be provable, not assumed. A pipeline with only a Bm25IndexWriter (no canonical entity store) genuinely can't know what's already ingested — returning False keeps the model call honest. Same logic for missing identifiers: without a resolvable entity_dir, the writer's own validation should be the thing that surfaces the error, not silent skips.

Tight enough that the smoke run exercised it across script invocations: a second invocation with prompt_version="v1" after the prior one ended on v2 correctly invalidated the cache and re-extracted, because the tuple changed even though source_hash didn't.

Error routing

Error policy — raise / skip / dead-letter

One on_error argument selects between three documented modes (SPEC §8.3):

ModeBehaviorUse case
raiseRe-raise; remaining workers cancelled before propagationDevelopment — fail loud
skipErrorEvent + record on report.failures; continueLossy backfills where one bad source shouldn't block progress
dead_letterSame as skip + write raw bytes + error.json (+ payload.json for ValidationError) under dead_letter_path/<source-id>/Production — preserve evidence for triage

Dead-letter layout

<dead_letter_path>/<source-id>/
├── raw.<ext>        # exact bytes the loader returned (if any)
├── error.json       # {source, error_type, message, traceback[]}
└── payload.json     # ValidationError.payload OR the unwritten ExtractionResult
Why preserve the unwritten ExtractionResult too: if extraction succeeded but the writer rejected it (schema violation, identifier mismatch), the raw bytes alone don't tell you what the model actually produced. Persisting the parsed result makes the failure debuggable without re-paying the extraction cost.
Tradeoff accepted: raise mode cancels in-flight workers via task.cancel() rather than letting them complete. A 500-doc batch that fails on doc #3 stops there, forfeiting docs #4-#500 even though they might have succeeded. Intentional: raise is the dev-loop mode where you want the traceback now, not after waiting for the batch to drain. Use skip or dead_letter in batch contexts.
Async shape

Concurrent execution + event ordering

Documents run concurrently via an asyncio.Semaphore bounded by the concurrency arg (default 4). Each worker buffers the events it would have emitted into a local list; the pipeline yields each worker's full event list when the worker completes via asyncio.as_completed. 

async def worker(src: Path) -> list[Event]:
    events: list[Event] = []
    async with sem:
        await self._process_source(src, seq, events, report)
    return events

tasks = [asyncio.create_task(worker(s)) for s in sources]
for coro in asyncio.as_completed(tasks):
    worker_events = await coro
    for evt in worker_events:
        yield evt
Tradeoff accepted: this is not truly live streaming. A document's events all surface together when that document finishes, not as each step happens. For ingestion — where the heavy cost is one model call per document and documents take seconds to minutes — the granularity is fine. A real streaming variant would need a producer/consumer queue with sentinel-based shutdown; the simpler as_completed shape covers the actual use case (progress bar in the CLI, throughput in audit logs) without that complexity.

Cancellation on raise

When on_error="raise" and a worker raises, the iterator's except BaseException branch cancels the remaining tasks and awaits their settlement before re-raising: 

except BaseException:
    for t in tasks:
        if not t.done():
            t.cancel()
    await asyncio.gather(*tasks, return_exceptions=True)
    raise

The gather(..., return_exceptions=True) is deliberate: cancelled tasks shouldn't shadow the original exception. The first failure is what the caller sees.

Forward-compat sidecar

The BM25 sidecar

reigner/ingestion/writers/bm25.py Bm25IndexWriter doesn't index anything. It dumps a JSON list of per-entity entries — concatenated section text, identifiers, source path — and T-10 (which delivers the actual BM25 search tools) will read this same file. The format is the contract: 

[
  {
    "id": "AAPL/2024",
    "identifiers": {"fiscal_year": "2024", "ticker": "AAPL"},
    "text": "<section1>\n\n<section2>\n\n...",
    "source": "/path/to/raw/AAPL_2024.pdf"
  },
  ...
]

Each write does an upsert (dedup by id) and an atomic replace (tmp = path + ".tmp"; tmp.write_text(...); tmp.replace(path)). Concurrent calls from pipeline workers are serialized through an asyncio.Lock the writer owns, so multiple workers on one event loop can update the same sidecar without losing entries.

Deferred to T-10: tokenization, inverted index, scoring, query API. The sidecar is the on-disk format only — everything search-side lives in tools/search/bm25.py, which is its own task and its own surface.
Why ship the sidecar now anyway: the pipeline already has the data flowing through it. Writing the sidecar costs nothing extra and means T-10 has real fixture data the moment it lands. The alternative — landing the pipeline without a search writer, then revisiting later — would have either left a hole in writers=[...] or required users to BYO a writer to get retrieval working.
Out of scope, on purpose

What was deliberately deferred

  • Multi-transform chaining. The constructor accepts transforms: Sequence[Transform] as the SPEC example shows, but enforces len(transforms) == 1 at construction. The list shape is forward-compatible with non-LLM transforms (SPEC §8.4) landing later; defining their chaining semantics today would be guessing.
  • True streaming events. See §8 above. Per-worker buffering with asyncio.as_completed covers the in-scope use cases; a real-streaming variant is one queue away when somebody actually needs it.
  • URL ingestion via pipeline.run(url). UrlLoader exists and the pipeline registers schemes from it, but _discover only walks file paths today. URL-driven ingestion (a list-of-URLs source, or a manifest file) is a separate shape from directory-walking and didn't need to ship in v0.
  • Cross-source deduplication. Idempotency is per-source. Two raw files with byte-identical content under different filenames will be re-extracted twice. SPEC §8.5 calls this out explicitly — dedup is an upstream concern.
  • Progress percentages / ETA. The report carries wall_clock_seconds after the fact; live progress estimates aren't computed. A consumer can derive their own from succeeded + failed + skipped vs. discovered.

For the reviewer

Reviewer's checklist

If you're reviewing this branch, the highest-leverage things to verify:

  • Read _process_source top-to-bottom. It's the per-document state machine — every guarantee in §8.3 has a touch point in this method. If the control flow isn't obvious, the abstraction is wrong.
  • Sanity-check _is_already_extracted: the three early-returns (no artifact writer, no identifiers, manifest missing/corrupt) all return False — confirm that's the right safe default for each. Returning True by mistake would silently skip real work.
  • Confirm the cancel-on-raise path in run_stream: tasks cancelled with gather(..., return_exceptions=True) so the original exception isn't shadowed by CancelledError from siblings.
  • Look at _invoke_writer's asyncio.to_thread wrap. Multiple workers can hit ArtifactWriter.write_entity concurrently — verify the writer's UUID-named staging dirs (T-13's atomicity protocol) make this safe.
  • The default identifiers_fn stringifies values ({k: str(v) for k, v in raw_ids.items()}). Spot-check that this matches what ArtifactWriter expects for entity_path placeholders.
  • Verify Bm25IndexWriter survives a corrupt sidecar: _read_existing swallows JSONDecodeError and starts fresh. Worth confirming you're OK with that recovery behavior — the alternative is hard-failing the write.
Mental model to carry into the review: this PR is the Layer-C runner. Every method here exists either to deliver one of §8.3's five guarantees or to provide a configurable seam (identifiers, source IDs, on-error) for users whose corpus doesn't match the defaults. Anything else would be scope creep into the user's domain.
