Where we were

The starting point

#28 (already on main) built the eval seam but shipped zero concrete checks. In reigner/eval/ there was: checks.py — CaseRun (a captured run record: final answer, event stream, citations, elapsed, usage), CheckResult (a ternary pass/fail/na verdict), and a @check name→function registry; runner.py — EvalSuite.run() and render_scorecard(); and cases.py — the declarative EvalCase.

What was missing was the actual judgement: nothing scored a run. The runner could drive a harness and render a table, but every column it could show was a check that didn't exist yet, and there was no command-line way to invoke any of it.

Why this split: #28 deliberately froze the shape of a check — (EvalCase, CaseRun) -> CheckResult — so the five analyzers could land with zero edits to the runner. T-29 is purely "fill in the registry," which is why this PR touches no runner control flow beyond adding a second renderer.

Architecture

The shape of a check run

The runner captures one CaseRun per case and fans it out to every resolved check. No check ever touches the live loop — they read a finished record. Registration happens at import time via the @check decorator; eval/__init__.py imports the five modules so the registry is populated before get_check() resolves a name.

EvalSuite._run_case (runner.py, from #28) │ drives harness.session(profile).run_stream(query) │ captures → CaseRun{ final, events, citations, elapsed, usage } ▼ ┌─────────────── for each resolved check fn ───────────────┐ │ fn(case, run) -> CheckResult(name, pass|fail|na, detail) │ └──────────────────────────────────────────────────────────┘ │ │ faithfulness answer numbers ⟷ citation values │ coverage expected sources ⟷ tool-call paths │ repeated_calls (name, args) keys → any seen ≥ 2× │ entity_resolution ambiguous case → clarified vs answered │ latency_cost usage + elapsed → vs max_tokens/max_seconds ▼ SuiteResult ──► render_scorecard() (the §15.2 table) └─► render_report() (scorecard + per-case detail) [new] @check("name") at import ──► module-level registry ──► get_check(name)
Why checks read a CaseRun, not the loop: every §15.1 check is computable from a completed run. Decoupling the verdict from the live loop makes each check a pure function — trivially unit-testable with a hand-built record — and keeps the runner the only thing that drives a model.
The hard one

Faithfulness — numbers must trace to citations

eval/faithfulness.py The trust property (SPEC §22 Week-6 criterion 3): every number the agent asserts in its answer must map to a registered citation. The check extracts numbers from the answer, extracts numbers carried by the run's citations, and fails on the first answer-number with no citation backing it. Matching is scale-tolerant (so "$31.4 billion" matches a stored 31.4) with a relative epsilon.

Number extraction is token-based

The first implementation scanned the answer character-by-character with a regex. That kept inventing numbers that were never claims. Running a real model (gpt-5.5) over a real corpus surfaced three distinct phantom-number bugs in a row:

Answer textChar-scan extractedReality
… in 2022-23.-23fiscal-year range
… in 2022–23. (en-dash)23fiscal-year range
Amity University (IR-E-U-0497) …-497institute id
**449 faculty** (markdown)nothing → false n/aa real claim, missed

The fix was to stop scanning and instead tokenize, accepting a number only if a whole whitespace-delimited token is numeric:

# strip wrapping punctuation/markup, then require the ENTIRE token to be numeric
_EDGE_PUNCT = "()[]{}\"'.,;:!?–—-*_`#~"
for token in text.split():
    cleaned = token.strip(_EDGE_PUNCT)
    m = _NUM_RE.fullmatch(cleaned)        # fullmatch, not search
    if m is None:
        continue
    ...
    if not scale and "." not in raw and 1900 <= value <= 2099:
        continue                          # calendar year, not a metric
Why token-based (the lead decision): a character-scanning regex will always pull digit runs out of identifiers, version strings, and date ranges — the bugs above are not edge cases, they're the norm for prose a model writes. Requiring a whole token to be numeric (plus stripping markdown edges and fiscal-year ranges first) is what makes the check usable on real answers instead of only on hand-written test strings. Every row above is now a regression test.
Tradeoff accepted: faithfulness is numeric-only and deterministic. It does not LLM-judge paraphrased qualitative claims, and a number that coincidentally equals an unrelated citation value passes. This is numeric faithfulness, not semantic — chosen so eval runs are reproducible and free. A semantic check can be added later via the same async-capable seam.

Verdicts: pass when every number is cited; fail on the first uncited one (named in the detail); na when the answer has no numeric claims.

The rest of the registry

The other four checks

coverage — did it retrieve the answer's source?

eval/coverage.py Distinct from faithfulness (which scores citing), coverage scores retrieving. For each expected_citations entry it takes the source (the part before #, e.g. IR-E-U-0497/2024/metrics.json) and requires a retrieval ToolCallEvent to have touched it via a path / file_path arg (equal or a path-segment prefix). na when the case lists no expected citations.

Why retrieval, not citation: an agent can be right by luck. Scoring whether it actually read the source artifact is a different, stronger signal than whether the prose happened to match — and keeps coverage from collapsing into a duplicate of faithfulness.

repeated_calls — loops & redundant fetches

eval/repeated_calls.py Builds an identity key (tool_name, canonicalized args) for every ToolCallEvent (reusing canonicalize_locator so arg key order doesn't matter) and fails if any key occurs ≥ 2×, naming the offender and count. na when no tool calls were made.

entity_resolution — clarify vs guess

eval/entity_resolution.py Scoped to ambiguous cases: na unless the case sets expected_clarification: true; for those, pass if a ClarificationEvent fired, fail if the agent answered anyway (guessed). It complements — rather than duplicates — the runner's always-on intrinsic expected_clarification check, which scores both directions for any case that sets the flag.

latency_cost — budget per case

eval/latency_cost.py Reports total tokens + elapsed seconds in its detail (e.g. "8.1k tok · 1.2s") and fails only if the case set max_tokens / max_seconds and the run exceeded it. Those two budgets are the only new fields on EvalCase in this PR (validated: positive number or absent; bool rejected).

Tradeoff accepted: the SPEC §15.2 scorecard shows a dollar Cost column, but TokenUsage carries only token counts and CaseRun has no model name — so a price isn't computable without new pricing/plumbing. The check reports tokens + wall-clock rather than fabricating a $ figure.
Command line

The reigner eval command

cli/eval.py Mirrors the other CLI commands (env load, ConfigError handling, --config/-c). Cases come from eval.cases in reigner.yaml (default eval/cases.yaml); checks are resolved --check flags → eval.checks in config → all registered. --case filters by id. Exit codes: 0 all passed, 1 some failed, 2 usage error.

Why fail-fast resolution order: bad --profile, unknown --case, and unknown --check are all validated before the harness is built — so a typo exits with a friendly message and never costs a model call. The check names are resolved up front for the same reason.

One small footgun handled: the module is cli/eval.py, so __main__.py imports it as eval as eval_cmd to avoid shadowing the eval builtin. The two repeatable list options (--case, --check) use Annotated[...] so the typer.Option(...) call isn't a mutable default (ruff B008).

Beyond the scorecard

--report: query, response, trace, citations

eval/runner.py The scorecard answers "did it pass." render_report() answers "what actually happened." It embeds the scorecard, then for each case emits the query, the agent's response (or (clarified)), the ordered tool-call trace, registered citations, the token/time cost, and every check's verdict with its reason.

Why it lives in runner.py, next to render_scorecard: it's a pure function over SuiteResult, so the CLI (reigner eval --report) and the tests share one renderer with no model dependency. --report and --json are mutually exclusive (passing both → usage error).
Out of scope, on purpose

What was deliberately deferred

  • Dollar cost in the scorecard. No pricing table and no model name on CaseRun; latency_cost reports tokens + wall-clock. Adding $ later is purely additive.
  • LLM-judged faithfulness. The seam is async-capable, but all five checks stay deterministic for reproducibility. A semantic faithfulness check can register alongside the numeric one without touching it.
  • Cycle detection in repeated_calls. It flags exact (name, args) duplicates, not repeating sequences (A,B,A,B), and has no tolerance knob — one accidental re-fetch fails the case. A threshold/cycle-aware variant is a clean follow-up.
  • The eval-vs-clarification profile tension. The default eval profile strips request_clarification for determinism, so an expected_clarification: true case can't clarify under it — evaluate those with --profile read_only. Reconciling this in the registry is left for later.
Verification

How it was tested

26 new tests in this PR (verified by grep -c 'def test_'): 24 in tests/eval/test_checks.py and 2 added to tests/eval/test_scorecard.py for render_report. The full tests/eval/ suite is 48 tests; the whole repo is 804 passing.

  • Per check: pass / fail / na path for each of the five.
  • Faithfulness regressions: scale-normalized match, billions-stored citation, uncited → fail, no-claims → na, calendar years, fiscal-year ranges (hyphen / slash / en-dash), ID-embedded digits, and markdown-bolded numbers.
  • Registration: all five names appear in registered_checks().
  • Report rendering: an answered case (query / response / trace / citation / verdict / cost all present) and a clarified case ((no final answer), (no tool calls), (none) citations).

Checks are tested against hand-built CaseRun fixtures — no live harness, no model — which is the payoff of the pure-function design. The end-to-end path (reigner ingest → reigner eval) was additionally exercised against a real corpus with a live model; that run is what surfaced the faithfulness bugs above.

For the reviewer

Reviewer's checklist

Highest-leverage things to spot-check:

  • Read faithfulness._numbers() against the four phantom-number rows above — confirm token-based extraction + the fiscal-year-range strip + the year heuristic actually cover each, and that the regression tests assert them.
  • Sanity-check the scale-tolerant match (_FACTORS / relative epsilon): a genuinely wrong number must still fail, not slip through a scale factor.
  • Confirm coverage's path matching is segment-aware — that AAPL/2024 doesn't spuriously "cover" AAPL/2024x/....
  • Verify the CLI resolves checks/cases and validates --profile before Harness.from_config — no model call on a typo (the three usage-error paths exit 2).
  • Note the default --profile eval strips clarification: an ambiguous case will fail under it. Confirm that's the documented, intended behavior, not a bug.
  • Check eval/__init__.py imports the five check modules — without those imports the @check decorators never run and get_check can't resolve them.
Mental model to carry in: the runner and seam are #28's; this PR is the judgement layer. The one decision that carries the most weight is token-based number extraction in faithfulness — it's the difference between a check that works on real model prose and one that only works on tidy test strings.
