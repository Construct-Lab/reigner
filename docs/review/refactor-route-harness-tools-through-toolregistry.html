Where we were

The starting point

ToolRegistry had been merged earlier with profile filtering baked in (full / read_only / eval), but the Harness never adopted it. Harness.tools was still a flat list[RunnableTool], name uniqueness was enforced by hand in a one-off _check_tool_name_collisions helper, and Session.run(profile=...) raised NotImplementedError for anything other than "full" with a stale requires the tool registry message.

As a result three pieces of registry functionality were sitting unused: the two non-default profiles, the name-uniqueness machinery, and the single registry object the server / CLI / eval runner / future MCP exporter could hand around.

Why now: the issue body called this a T-07 integration gap. Every consumer that wanted a filtered surface — eval, future MCP export, plugin loaders — was blocked behind one missing wiring step. Closing it now keeps the prerequisite chain short.

Architecture

The shape of the refactor

Two layers — build-time and runtime — both now thread through one ToolRegistry.

BUILD-TIME Harness.from_config(path) ───────────────────────────────────────────────────────────────── reigner.yaml ─┐ ArtifactStore ┼──► register() ──► ToolRegistry (stores ToolSpec) Bm25Index ────┤ │ cfg.tools.custom ┘ │ duplicate name? tools=[…] extras ─────► register() └─► ToolRegistrationError │ ▼ Harness │ session(profile=…) ▼ Session(profile) │ ▼ AgentState .registry = harness.registry .profile = session.profile RUNTIME one turn of run_loop ───────────────────────────────────────────────────────────────── tools_by_name = {a.name: a for a in state.registry.for_profile(state.profile)} │ adapter.call(prompt, [a.spec for a in │ pseudo? ──► _dispatch_pseudo runnables]) ──────┤ (inline) │ real call ────────┴──► execute_batch └─► tools_by_name[name].run(args) └─► emit ToolResultEvent
Why both registry and profile live on AgentState: the issue's wording mixed state.registry with session.profile. Putting both on state keeps run_loop's signature unchanged — every loop input already comes off state. Session still owns profile publicly; it just hands a copy to AgentState at construction. One assignment, no sync hazard.
Tradeoff accepted: for_profile() constructs fresh RunnableToolAdapter instances on every call. With ~10 tools per harness and one filter per turn, that's a non-issue; if a profiler ever flags it, the fix is to memoise inside the registry — caller code wouldn't change.

Runtime dataflow — three sessions, one registry

A walkthrough of what actually happens when a user spawns sessions at different profiles from the same Harness. The registry is built once; nothing about the spawn mutates it.

#   len(h.registry) == 12

t=1 · spawn three sessions

full      = h.session(profile="full")        # full.profile      == "full"

#   each AgentState carries its own `.profile`.
#   the registry is never mutated.

state.registry.for_profile("eval")
#   ─► drops `my_custom_write` (readonly=False)
#   ─► drops `escalate_to_oracle` (defeats determinism)
#   ─► drops `request_clarification` (pauses the loop)

Why filter on every turn instead of once at session start: profile is constant for a session's lifetime, so the filter result is stable. Re-filtering is cheap (a list comprehension over ~10 specs + one adapter wrap each) and keeps the loop free of cached intermediate state. If profile ever becomes dynamic, the loop is already shaped for it.

Per-piece deep dive

Registry — accept-and-wrap

reigner/tools/registry.py Two changes. First, register() grows a third input shape; second, for_profile() changes its return type. 

def register(
    self, func_or_spec: Callable[..., Any] | ToolSpec | RunnableToolAdapter
) -> ToolSpec:
    if isinstance(func_or_spec, ToolSpec):
        spec = func_or_spec
    elif isinstance(func_or_spec, RunnableToolAdapter):
        spec = func_or_spec.spec     # ← new branch
    else:
        spec = _spec_of(func_or_spec)
    if spec.name in self._specs:
        raise ToolRegistrationError(...)
    self._specs[spec.name] = spec
    return spec

def for_profile(self, profile: Profile) -> list[RunnableToolAdapter]:
    ...
    return [RunnableToolAdapter(spec=s) for s in specs]   # ← wraps on the way out
Why store specs and wrap on output: the spec is the canonical record (one per name, mutated nowhere). The adapter is a thin runtime façade with .run(args). Storing adapters would duplicate state; storing specs keeps the registry as the single source of truth and lets __iter__ / get() return specs cleanly.
Tradeoff: __iter__ yields specs but for_profile() yields adapters. They look similar but the types differ. Tests now have to pick the right entry point for what they want — call sites that need .run use for_profile("full"), call sites that just check names iterate the registry directly.
Per-piece deep dive

State — registry + profile on AgentState

reigner/harness/state.py The placeholder ToolSpec Protocol that lived at the top of state.py served as a forward-declaration stub while the real spec was being built in reigner/tools/base.py. Now that the real one exists and structurally satisfies the same surface, the placeholder is gone — but it's still re-exported by name from state.py so the four model adapters that import ToolSpec from there don't need to change. 

from reigner.tools.base import ToolSpec     # ← imported, not redefined
from reigner.tools.registry import ToolRegistry
from reigner.types import Profile
...
@dataclass(kw_only=True)
class AgentState:
    ...
    registry: ToolRegistry = field(default_factory=ToolRegistry)
    profile: Profile = "full"
    ...

def _stable_text(self) -> str:
    tool_lines = [
        json.dumps({...}, sort_keys=True, separators=(",", ":"))
        for t in self.registry.for_profile(self.profile)    # ← was self.tools
    ]
    return self.role + "\n\n" + "\n".join(tool_lines) if tool_lines else self.role
Why _stable_text also goes through the registry: the stable preamble carries the JSON-serialised tool list that's part of what the model sees. If it iterated self.tools (all registered tools) but the model adapter was passed for_profile(profile) (filtered), the cached preamble would advertise tools the model couldn't actually call. They have to agree.
Per-piece deep dive

Harness / Session — one registry, one profile

reigner/harness/agent.py Harness.tools → Harness.registry. from_config builds the registry by calling register() in the canonical wiring order (artifacts → search → custom → caller extras). Duplicate-name detection moves from _check_tool_name_collisions (deleted) to the registry's own ToolRegistrationError. 

registry = ToolRegistry()
for t in (*artifact_tools, *search_tools, *custom_tools, *(tools or [])):
    registry.register(t)   # raises ToolRegistrationError on duplicate names

return cls(
    adapter=adapter,
    settings=cfg.settings,
    registry=registry,
    role=role_text,
    oracle_adapter=oracle_adapter,
)

Session.session(profile=...) stops raising NotImplementedError and threads the profile through to the new AgentState. Session.fork(...) preserves self.profile in the child session so a forked A/B run can't accidentally switch surfaces under the user.

Why drop Harness.tools entirely instead of keeping it as a convenience: two ways to say the same thing breeds drift. The acceptance criteria call list(h.registry) out explicitly, and direct-construction tests are a one-line change. The end state is cleaner than the migration cost.
Subtle fix

A subtle mypy fix on two Protocols

RunnableToolAdapter exposes name, readonly, description, and friends as @property (read-only descriptors that delegate to self.spec). When the loop's RunnableTool Protocol declared name: str as a bare class-body attribute, mypy refused the adapter on the grounds that the Protocol member expected a settable variable.

Both RunnableTool Protocols (loop.py and parallel.py) now declare these members as @property: 

@runtime_checkable
class RunnableTool(Protocol):
    @property
    def name(self) -> str: ...
    @property
    def readonly(self) -> bool: ...
    async def run(self, args: dict[str, Any]) -> Any: ...
Why two near-identical Protocols stay separate for now: consolidating them into one shared definition is the right end state, but each module's Protocol is intentionally thin and the duplication is local. Folding them is a follow-up worth its own commit — out of scope here.
Out of scope, on purpose

What was deliberately deferred

  • Plugin system (issue #26). External tool packages registering via entry points is a registry-shaped concern, but its own refactor — touches discovery, version pinning, trust. The shape this lands lets a plugin loader call registry.register(adapter) with no extra surface.
  • MCP server export (issue #23). The exporter will iterate h.registry and translate each spec to an MCP tool descriptor. Out of scope here; the integrated registry is the prerequisite, not the work.
  • Custom-profile registration. Profiles today are a fixed Literal["full","read_only","eval"]. A user can't yet say read_only minus bm25_search. Deferred until a real need surfaces.
  • Memoising for_profile(). Fresh adapters are allocated every call. Easy to cache later if a profiler ever flags it; not worth the cache-invalidation surface today.
  • Unifying the two RunnableTool Protocols. loop.py and parallel.py each declare their own. Consolidation is a separate, mechanical commit.
What's not deferred: the integration this issue called out. read_only and eval profiles are live; the hand-rolled collision check is gone; one registry object is now what every downstream consumer asks for.

For the reviewer

Reviewer's checklist

If you're reviewing this branch, the highest-leverage things to spot-check:

  • Read reigner/harness/agent.py from_config + Session.__init__ as a pair — confirm the registry is built once, passed by reference, and never copied. Three sessions sharing one registry is correct; two registries diverging silently would be a regression.
  • Confirm state.py exports ToolSpec via __all__. Four adapter modules import it from there; removing the re-export would silently break their type hints.
  • Trace one turn through loop.py at the top of run_loop: runnables is built once per call, and the model adapter receives [a.spec for a in runnables] (specs, not adapters). Adapters never escape the loop module.
  • The _stable_text in state.py now iterates self.registry.for_profile(self.profile). If you swap it back to self.registry (unfiltered) the cached preamble would lie about the tool surface — make sure the test test_eval_profile_also_drops_oracle_and_clarification would catch that.
  • Check the new @property declarations on both RunnableTool Protocols. They look like a no-op but RunnableToolAdapter's descriptor-based name/readonly only structurally match a Protocol that uses @property.
  • Spot-check that Session.fork forwards self.profile. A fork that silently switched profile would defeat A/B comparison entirely.
  • Verify the acceptance criteria from the issue: no T-07 string remains in reigner/harness/*.py; _check_tool_name_collisions is gone; profile="read_only" and profile="eval" build a session without raising.
Mental model to carry into the review: the registry is the single source of truth for which tools exist; the profile is the single source of truth for which of them this session sees; the loop is the only place those two are combined. Every other consumer (model adapter, eval runner, future MCP exporter) reads off exactly one of those two — never both, never something derived from a third.
