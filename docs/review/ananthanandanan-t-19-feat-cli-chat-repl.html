Where we were

An agent with no front door

Before this PR, the harness was complete enough to run end-to-end — Harness.from_config, Session.run_stream, the full event protocol — and reigner init could scaffold a project. But there was no user-facing way to talk to the agent. The CLI knew how to set a project up; it didn't know how to use one.

T-19 closes that gap with one Typer command, reigner chat, that runs in three shapes from a single entry point: an interactive REPL for humans, --print "" for scripting, and --print --json for piping the full event stream to something else.

Why now: the loop and event protocol have been landed-and-tested for several tasks already; everything downstream (eval runs, demos, the issue tracker's "can you just try it" conversations) needs a way to hit it from a shell. T-19 is the smallest surface that unblocks all of them.

Architecture

The shape of the command

One Typer function (_chat) routes on flags to one of two coroutines: _run_print (headless) or _run_repl (interactive). Both consume the same Session.run_stream iterator the harness already exposes; nothing about the loop changes.

┌──────────────────────────────────────────┐ │ `reigner chat [--print Q] [--json]` │ │ Typer dispatch in chat.py::_chat │ └──────────────┬───────────────────────────┘ │ ┌──────────────┴───────────────┐ ▼ ▼ ┌───────────────┐ ┌────────────────┐ │ _run_print │ │ _run_repl │ │ one-shot │ │ prompt_toolkit│ └──────┬────────┘ └──────┬─────────┘ │ │ │ query │ query (Enter) ▼ ▼ ┌─────────────────────────────────────────────┐ │ Session.run_stream(query) ─ async gen ─ │ │ (loop.py, unchanged from T-05/T-06) │ └────────────┬────────────────────────────────┘ │ Event stream ▼ ┌─────────────────────────┐ ┌─────────────────────┐ │ _run_print: │ │ _run_repl: │ │ plain → final.text │ │ _render_event() │ │ --json → to_json(ev) │ │ compact lines + │ │ │ │ rich.Panel final │ └─────────────────────────┘ └─────────┬───────────┘ │ mid-run Enter / Alt+Enter: ▼ Session.steer(text, mode) │ ▼ AgentState.enqueue_steering │ loop drains at next iteration: ▼ append user Turn(message) yield SteeringAcceptedEvent
Why one command, not three: the question "can I run my agent" has one answer in the user's head. Splitting chat, print, and json into separate Typer commands would scatter argument validation and double the surface for the same underlying behavior. Flags compose; commands don't.
SPEC §5.6

Steering, end-to-end

Steering had been deferred since T-05: Session.steer raised NotImplementedError, and the loop never consulted state.pending_steering. SPEC §22 scheduled the feature for Week 7, but T-19's own bullet says "interactive REPL with interrupt/queue steering" — a REPL whose mid-run keys silently no-op is the kind of footgun this project explicitly rejects. So both halves landed here.

Producer — Session.steer

async def steer(self, message: str, mode: SteeringMode = "interrupt") -> None:
    """Enqueue a user steering message; consumed at the next loop boundary."""
    self._state.enqueue_steering(message, mode)

Three lines. AgentState already owned the queue and the drain primitives from T-03; the only thing missing was the public method on Session that put items in.

Consumer — drain at the top of every iteration

reigner/harness/loop.py Right after state.refresh_context() and before progressive compaction, the loop checks for queued steers and folds each into the history as a user turn so the next adapter.call sees it: 

if state.has_pending_steering():
    for message, mode in state.consume_steering():
        state.append_turn(Turn(role="user", content=message))
        yield SteeringAcceptedEvent(
            seq=next_seq(),
            session_id=session_id,
            turn=state.iterations,
            message=message,
            mode=mode,
        )
Why drain at the iteration boundary, not mid-tool: the loop is cooperative — it only yields control at await points, and by the time control reaches the drain site, any prior turn's tool calls have already completed. The iteration boundary is the "next tool boundary" SPEC §5.6 refers to. This also keeps "interrupt" and "queue" behaviorally equivalent at this layer: both append-as-user-turn at the same site. The mode is preserved on the emitted event so callers (and future intra-iteration drain sites, if any) can distinguish them.
Tradeoff accepted: a steer enqueued mid-iteration won't be acted on until the current adapter.call + tool batch finish. There is no preemption of an in-flight model call. For interactive use this is invisible (drains happen at human timescales relative to per-iteration cadence); for very long tool calls it means a delay between keystroke and effect. SPEC §5.6 accepts this — the contract is "next boundary," not "preempt now."
Headless modes

--print and --print --json

reigner/cli/chat.py _run_print drains the event stream once and exits. Two output shapes:

InvocationStdoutStderrExit
chat --print "Q"Just final.text—0
chat --print "Q" --jsonND-JSON of every event (via to_json)—0
chat --json (no --print)—--json only makes sense with --print2
chat --print "Q" w/ no reigner.yaml—no reigner.yaml … run `reigner init` first2
Loop ends on clarification (plain)—Hint to use interactive mode2
Why plain mode emits only the final answer: --print is the shape that gets piped into shell substitutions and CI scripts. Mixing status chatter into stdout breaks $(reigner chat --print …) in the most annoying way possible — silent corruption of the consumer. Everything diagnostic goes to stderr; stdout is the answer or nothing.

Exit codes

  • 0 — final answer produced.
  • 1 — runtime error (non-recoverable ErrorEvent, no final answer).
  • 2 — usage error (missing config, --json without --print, clarification in headless mode, no TTY for interactive).
Interactive UX

The REPL — prompt_toolkit + rich

reigner/cli/chat.py The interactive mode is a PromptSession with custom key bindings, wrapped in patch_stdout(raw=True) so streamed rich output above doesn't tear the live prompt line. 

kb = KeyBindings()

@kb.add("enter")
def _on_enter(event):
    buf = event.app.current_buffer
    text = buf.text.strip()
    if not text:
        return                       # empty Enter is a no-op
    if running.is_set():
        asyncio.create_task(session.steer(text, "interrupt"))
        buf.reset()                  # mid-run: steer + clear
    else:
        event.app.exit(result=text)  # idle: submit

@kb.add("escape", "enter")           # Alt+Enter
def _on_alt_enter(event):
    ...  # steer(text, "queue")
Why Enter changes meaning by state: users already know Enter from every other shell — "submit the line." Reusing the same key for "steer the running agent" keeps the muscle memory; the running asyncio.Event picks the right interpretation. Alt+Enter gives an explicit way to queue instead of interrupt, matching SPEC §5.6's two modes.

Rendering

_render_event() maps each event type to a compact line — · status: …, → tool_call name(args), ← tool_result (with optional truncated / cached tags), ~ compaction, ⇡ oracle, ⇲ steering accepted, etc. The final answer is the only event that gets a full rich.Panel(border_style="green"), so visually scanning a scrollback for "where did this run end" is one glance.

Tradeoff accepted: no live spinner / progress animation. A spinner means a background task fighting patch_stdout for the bottom row; intermediate StatusEvent lines carry enough signal for v1. Pretty progress UI is deferred.
Lifecycle

Cancel, quit, and the two Ctrl+Cs

The REPL has three different "stop" semantics that have to stay distinguishable so the user is never stuck:

KeysStateEffect
Enter on empty bufferanyno-op
/exit or /quitidleprint bye., return
Ctrl+D (EOF) / Ctrl+Cidleprint bye., return
Ctrl+Crunningcancel the current run task, REPL stays
Ctrl+C againidle (after cancel)quit
Why Ctrl+C doesn't quit mid-run: the most common reason a user hits Ctrl+C during a long agent run is "this is going the wrong way, stop." Killing the REPL on top of that would force them to re-launch the process and re-load config just to ask a different question. Cancel-the-task-first matches every other long-running CLI shell people use.

Non-TTY refusal

_run_repl checks sys.stdin.isatty() up front and refuses with exit 2 and a pointer to --print if stdin is piped. This is what catches CliRunner invocations of bare chat in tests and any accidental echo "foo" | reigner chat.

Test pattern

FakeAdapter as the test contract

tests/cli/conftest.py Tests don't have API keys and can't reach a real model. The fixture bypasses Harness.from_config entirely and constructs a Harness directly with the FakeAdapter that already exists in tests/harness/test_loop.py: 

def _final(text: str = "done") -> ModelAction:
    return ModelAction(
        is_final_answer=True, text=text, tool_calls=[],
        usage=TokenUsage.empty(), stop_reason="end_turn",
    )

@pytest.fixture
def make_session():
    def _build(actions=None):
        adapter = FakeAdapter(actions=list(actions or [_final("hello world")]))
        harness = Harness(adapter=adapter, tools=[], role="TEST",
                          settings=SettingsConfig())
        return harness.session()
    return _build

@pytest.fixture
def patch_build_session(monkeypatch, make_session):
    def _install(actions=None):
        session = make_session(actions)
        monkeypatch.setattr(chat_module, "_build_session", lambda _p: session)
        return session
    return _install
Why monkeypatch _build_session and not Harness.from_config: the CLI's only coupling to config is one function call. Patching at the seam keeps the test from having to fake reigner.yaml, model adapter discovery, tool resolution, or any of the legitimate from_config machinery — none of which T-19 actually exercises.

Driving the REPL without a terminal

test_repl_runs_one_query_and_exits uses prompt_toolkit's own test machinery — create_pipe_input() + DummyOutput() + create_app_session() — to send "ask\n/exit\n" through the same key-binding stack a real terminal would. It then asserts the FakeAdapter recorded exactly one Prompt call and the session's event log contains a FinalAnswerEvent. Real bindings, real PromptSession, no TTY required.

Out of scope, on purpose

What was deliberately deferred

--resume <session_id>. Replaying a prior JSONL session is T-23 territory; the persistence format isn't finalized.
Mid-REPL clarification answer flow. Today a ClarificationEvent is rendered in a yellow Panel and the loop ends. A full "type your answer and resume the run" flow needs loop-side hooks not yet in place.
Live spinner / progress bar. Streamed status lines are the v1 progress signal; an animated bottom-bar spinner fighting patch_stdout is more UI than v1 needs.
Windows TTY parity. prompt_toolkit works on Windows, but the cancel / patch_stdout interactions haven't been exercised there yet. macOS + Linux only for now.

What's intentionally not covered

  • Preemption of in-flight tool calls by a steer — out of scope for §5.6's "next boundary" contract.
  • --resume, clarification-resume flows — deferred (see above).
For the reviewer

Reviewer's checklist

  • Read reigner/cli/chat.py top-to-bottom — 300 lines, one Typer command + two coroutines. If it doesn't fit in one sitting, that's a finding.
  • Confirm the mid-run Enter binding doesn't submit (it should session.steer and reset the buffer). Empty Enter mid-run should also be a no-op, not an accidental empty steer.
  • Two Ctrl+C semantics: first cancels the running task, second (or one when idle) quits. Verify current_task is cleared in the finally so a post-cancel Ctrl+C doesn't re-target a dead task.
  • Stdout discipline in --print plain mode: only the final answer text reaches stdout; every diagnostic line uses typer.echo(..., err=True).
  • ND-JSON shape under --print --json: every emitted line must round-trip through from_json. The test asserts this on every line; double-check no print elsewhere bypasses it.
  • Session.steer's three-line body should remain a pure wrapper. All loop-visible behavior belongs on the consumer side in loop.py.
  • Steering drain site in loop.py: confirm it sits after refresh_context and before progressive, so steers are visible to the very next prompt build.
  • FakeAdapter imported from tests/harness/test_loop.py — the CLI tests ride on its calls list and actions queue.
  • patch_stdout(raw=True) wraps prompt_async; without it, streamed rich output above the prompt tears the input line. The mode matters (raw=True for rich-rendered output).
Mental model to carry into the review: this PR is the thinnest user-facing surface that lets a human (or a script) drive the existing harness, plus the SPEC §5.6 steering wiring that fell between T-05 and T-06 — producer on Session, consumer at the top of every loop iteration. The REPL's mid-run keys are honest end-to-end: keystroke → queue → next-turn prompt → model reacts.
